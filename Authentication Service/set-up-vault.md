# Auth Service — Vault Setup Guide

## Overview

Auth Service uses HashiCorp Vault Transit Engine for JWT signing. The private key never leaves Vault — Vault signs internally and returns only the signature. This guide covers setup, common errors, and daily workflow.

---

## How to Set Up Vault — All Scenarios

### Do you need unseal-vault.sh?

No. `setup-vault.sh` handles unsealing automatically in all cases. You never need to run `unseal-vault.sh` separately.

---

### Scenario 1 — First Time Ever

```bash
docker-compose up -d       # start all containers
./setup-vault.sh           # initialises + unseals + creates everything
                           # copy printed RoleId + SecretId into docker-compose.yml
docker-compose up -d authservice   # restart auth service with new credentials
```

---

### Scenario 2 — Every Day (containers restarted, volume intact)

```bash
docker-compose up -d       # start all containers
./setup-vault.sh           # unseals Vault + prints new SecretId
                           # copy new SecretId into docker-compose.yml
docker-compose up -d authservice   # restart with new SecretId
```

> RoleId stays the same. Only SecretId changes each time you run the script.

---

### Scenario 3 — Volume Deleted (`docker-compose down -v`)

Same as first time. Volume gone = Vault wiped = start fresh.

```bash
docker-compose up -d
./setup-vault.sh           # initialises everything from scratch
                           # new RoleId + SecretId generated
                           # copy both into docker-compose.yml
docker-compose up -d authservice
```

---

### Summary Table

| Scenario | Command | RoleId changes? | SecretId changes? |
|---|---|---|---|
| First time | `./setup-vault.sh` | Yes (new) | Yes (new) |
| Daily restart | `./setup-vault.sh` | No | Yes |
| Volume deleted | `./setup-vault.sh` | Yes (new) | Yes (new) |

One script handles all three cases. No manual unseal needed.

## vault-config.hcl

```hcl
storage "file" {
  path = "/vault/data"
}

listener "tcp" {
  address     = "0.0.0.0:8200"
  tls_disable = true
}

disable_mlock = true

ui = true
```

`disable_mlock = true` is required on Mac Docker. Without it Vault crashes with `CAP_SETFCAP` error.

## docker-compose.yml — Vault Section

```yaml
vault:
  image: hashicorp/vault:latest
  container_name: trading-vault
  ports:
    - "8200:8200"
  environment:
    VAULT_ADDR: http://0.0.0.0:8200
    VAULT_API_ADDR: http://0.0.0.0:8200
  volumes:
    - vault-data:/vault/data
    - ./vault-config.hcl:/vault/config/vault.hcl
  command: vault server -config=/vault/config/vault.hcl
  networks:
    - trading-network
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:8200/v1/sys/health?standbyok=true&uninitcode=200&sealedcode=200"]
    interval: 5s
    timeout: 3s
    retries: 10

volumes:
  vault-data:
```

## docker-compose.yml — Auth Service Section

```yaml
authservice:
  build:
    context: .
    dockerfile: ./Authentication Service/Dockerfile
  image: trading-authservice
  container_name: trading-authservice
  depends_on:
    vault:
      condition: service_healthy
  environment:
    ASPNETCORE_URLS: http://+:80
    ASPNETCORE_ENVIRONMENT: Development
    Vault__Address: http://trading-vault:8200
    Vault__KeyName: jwt-signing-key
    Vault__RoleId: <paste-from-setup-script>
    Vault__SecretId: <paste-from-setup-script>
  ports:
    - "5006:80"
  networks:
    - trading-network
```

Note: `Vault__Address` uses container name `trading-vault` not `localhost`. Double underscore `__` is how .NET reads nested config from environment variables.
