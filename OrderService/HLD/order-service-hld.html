1
entry point
🌐
Client
POST /api/order/create
▶
Sends POST /api/order/create with a Bearer JWT token in the Authorization header.

JWT contains: kid (key version), role, permission claims, expiry, issuer, audience.
2
asp.net middleware
🔐
UseAuthentication()
JWT Bearer middleware
▶
Intercepts every incoming request. Reads kid from JWT header.

Calls IssuerSigningKeyResolver (wired to JwtKeyResolver at startup via AddOptions) to get the matching public key for verification.
3
vault key resolution
🔑
JwtKeyResolver
IssuerSigningKeyResolver
▶
Wired into JWT middleware via AddOptions<JwtBearerOptions>.

Receives kid from middleware. Calls IPublicKeyProvider.GetPublicKeyAsync(kid). Returns IEnumerable<SecurityKey> to middleware.
🏛️
VaultPublicKeyProvider
IPublicKeyProvider
▶
Calls GET /v1/transit/keys/jwt-signing-key with X-Vault-Token header.

Parses all key versions from response. Picks version matching kid. Imports PEM using ImportSubjectPublicKeyInfo. Returns RsaSecurityKey with KeyId set.
🎫
VaultTokenProvider
IVaultTokenProvider
▶
Authenticates Order Service to Vault using AppRole (RoleId + SecretId from config).

POST /v1/auth/approle/login → returns client_token (1hr TTL). Used as X-Vault-Token in all Vault API calls.
🔒
Vault Transit Engine
GET /v1/transit/keys/jwt-signing-key
▶
Returns all public key versions in one response: { "1": {public_key}, "2": {public_key}, "3": {public_key} }

Order Service policy: read-only on transit/keys. Cannot sign, cannot access private keys. Private key never leaves Vault — ever.

Key auto-rotates every 30 days (auto_rotate_period=720h). Old versions kept until all tokens expire.
4
signature verification
✅
JWT Verification
RSA.Verify + claims validation
▶
ASP.NET middleware verifies using RS256 + PKCS1v15 (must match Vault signing algorithm).

Checks: signature (RSA verify with public key) → exp (not expired) → iss = "IdentityService" → aud = "MyAPI"

On success: sets HttpContext.User with all claims. Request proceeds to controller.
5
api layer
🎯
OrderController
POST /api/order/create
▶
No [Authorize] attribute — authorization happens inside MediatR pipeline instead.

Maps OrderRequest → OrderCreatedCommand via AutoMapper. Sends command via IMediator.Send(). Returns 202 Accepted with OrderId.
6
mediatr pipeline
// behaviors run in order
🛡️
AuthorizationBehavior
IPipelineBehavior — runs first
▶
Checks ICommandAuthorizationRegistry for the rule registered against this command.

Calls ICurrentUserService.IsAuthenticated — reads from HttpContext.User.

Calls IAuthorizationService.AuthorizeAsync with policy "CanCreateOrder" → RequireClaim("permission", "order:create").

Fail → throws ForbiddenException (403).
✔️
ValidationBehavior
IPipelineBehavior — runs second
▶
Runs FluentValidation on OrderCreatedCommand.

Validates: OrderType, ClientId, InstrumentSymbol, Quantity, Price.

Fail → throws ValidationException (400).
👤
ICurrentUserService
reads HttpContext.User
▶
Used by AuthorizationBehavior to read the authenticated user.

IsAuthenticated → HttpContext.User.Identity.IsAuthenticated
Principal → HttpContext.User (ClaimsPrincipal)

Set by UseAuthentication() middleware after JWT verification succeeds.
7
application layer
⚙️
OrderCreatedCommandHandler
IRequestHandler<OrderCreatedCommand>
▶
Creates Order entity via IOrderFactory.

Creates OutboxMessage with serialized OrderPlacedEvent payload.

Calls IOrderRepository.CreateOrderWithOutboxAsync — saves both in a single PostgreSQL transaction (transactional outbox pattern).
8
infrastructure layer
🗄️
PostgreSQL
Orders + OutboxMessages tables
▶
Stores Orders (status: PENDING → EXECUTED/REJECTED) and OutboxMessages in a single atomic transaction.

Transactional outbox ensures no message is lost even if RabbitMQ is down at publish time.
🐇
RabbitMQ
OrderPlacedEvent publisher
▶
OutboxBackgroundService polls for pending OutboxMessages every few seconds.

Publishes OrderPlacedEvent to RabbitMQ. Marks outbox message as processed.

ProcessingService consumes this event to execute/reject the order.
